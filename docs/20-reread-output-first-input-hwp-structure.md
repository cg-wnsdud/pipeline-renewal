# 20. 재판독 응답 형식·페이지 판독 한도·첫 입력 템플릿·HWP 구조 경로(2026-10-29)

전량 테스트(docs/19) 결과에서 찾은 문제 네 가지를 고쳤다. 기본 동작에 포함된다.

## 1. 재판독 응답 형식(region-reread/2) — 영역 문구 순서 오류의 직접 원인

**원인.** 영역 문구 순서 오류는 영역 검출이나 미배정 OCR 배치 문제가 아니었다. 두 단계가 겹쳐 생겼다.

1. 페이지 판독(줄인 페이지 한 장으로 영역 14~35개)에서 글자가 작으면 모델이 가나다순 OCR 후보 목록 순서를 따라 쓴다.
2. 기존 순서 검사(reading_order_conflict)가 이를 잡아 재판독을 요청하지만, 재판독 응답의 `changes` 배열(enum 목록)이
   문구를 다 쓴 뒤 `"missing_added"` 를 끝없이 반복해 4,000토큰에서 잘렸다. JSON 이 깨져 **맞게 읽은 문구까지 버려지고**
   1차 판독이 남았다.

| 근거(whole-test + e2e) | 수 |
|---|---:|
| 출력 한도에서 잘린 재판독 | 24(21건 전부 `changes` 반복, text 는 완성) |
| 그중 순서 충돌로 요청된 재판독 | 13 |
| 잘린 응답의 완성된 text 로 순서 검사 | 13/13 순서 맞음 |
| whole-test 실제 순서 오류 15개 중 이 경로 | 11 |

나머지 4개: 재판독이 함께 받은 1차 문구를 그대로 따름(w048 L005·w049 p2), 상자 밖 금액 추가로 선택 정책이 거부(w033),
항목명–값 2단(w071).

**수정.**

- `changes` 를 분류별 참/거짓 고정 키 객체로 받는다(반복 불가). 기록의 `reread_changes` 는 지금처럼 목록(참인 분류, 없으면 `none`).
- 응답이 잘려도 `text` 가 끝까지 쓰였으면 그 값만 꺼내(`salvage_text`) 같은 선택 정책(상자 밖 문구 유입·OCR 근거 덮임)으로 고른다.
  검토 코드 `reread_text_salvaged`. text 자체가 잘렸거나 region_id 가 다르면 꺼내지 않는다.
- 버전 `region-reread/2`. 이전 기록(`/1`)은 재구성 때 꺼내기를 하지 않는다(결과 재현).

**실제 검증**(24개 영역, 같은 crop·문맥 이미지·1차 문구로 새 형식 재판독, `work/reread2-live-2026-10-29/`): 23건 정상 종료
(출력 165~850토큰, 이전 전부 4,000에서 잘림). 1건(tt03 L003)은 GPU 를 함께 쓰던 실행 중 시간 초과(320초)로 1차 유지.
순서 충돌로 요청된 13개 중 **11개가 바로잡혔다**. 2개는 기존 선택 정책이 1차를 유지했다(w078 L017 상자 밖 문구 유입,
w089 L000 OCR 오독이 심해 OCR 근거 덮임 낮음). 반복 문구로 요청된 w018 L027 은 재판독 뒤 순서 검사에 걸린다(확인 필요).

## 2. 페이지 판독 출력 한도(page-tokens/1)와 잘린 페이지 응답의 부분 사용(page-partial/1)

- 한도 = `1500 + 2.5 × 판독 단위 영역들의 OCR 글자 수`, 최소 6,000 · 최대 12,000. 고정 12,000 일 때 정상 응답 345건의 최대
  출력은 3,844토큰이었고 이 식의 한도를 넘는 정상 응답은 0건이다. 반복 퇴화 응답 6건(건마다 160~250초)은 5건이 6,000, 1건이
  8,112에서 끊긴다. 설정 `page_max_tokens_rule`, 호출 기록 `max_tokens`.
- 잘린 페이지 응답에서 끝까지 쓴 영역 항목은 쓰고(`salvage_regions`) 나머지 영역만 실패로 둬 재판독한다. 쓴 영역은 맥락 사유
  `page_output_partial`. 이 처리를 표시한 요청 기록(`partial_salvage: page-partial/1`)에만 적용한다(이전 실행 재구성 그대로).
  whole-test 의 잘린 6건에서 끝까지 쓴 항목: w084 12/13, w094 7/13, w055 3/4·3/5, w100 2/35, w034 0/3.

## 3. 첫 입력 템플릿 유지(first-input/1)와 노이즈 대상 정리(R3)

**첫 입력 기준(사용자 지정).** 한 상품의 여러 입력(-N 파일)은 첫 입력에서 상품·템플릿이 정해지고 뒤 입력은 이어지는 화면이다.
whole-test 예금성상품(거치식) 9장(w042): 9장 모두 'NH전남광주통합특별시동행예금' 한 상품의 탭 화면인데, 페이지마다 따로 관측하면서
금리표 장을 '…동행 예금'·적립식으로, '예금종류: 큰만족실세예금' 항목을 별도 상품으로, 상세 탭 4장을 이름 없는 미확정 상품으로 만들었다.

`classify.first_input_rules`(관측·통합 결과 뒤, 모델 호출 없음):

| 규칙 | 내용 | 검토 코드 |
|---|---|---|
| M1 | 이름(canon: 공백·표기 통일)이 같은 그룹은 한 상품(앞 입력 그룹이 남고 템플릿도 그대로) | `merged_same_name` |
| M2 템플릿 | 파일이 둘 이상이면, 첫 파일 대상이 있는 그룹의 템플릿은 첫 파일 대상들의 템플릿 | `template_from_first_input`(바뀐 경우) |
| M2 이름 없음 | 뒤 입력에만 있는 이름 없는 대상 그룹은 첫 입력 상품(이름 있는 첫 그룹)에 잇는다. 그 그룹의 검토 코드도 함께 남긴다 | `unnamed_attached` |

뒤 입력에만 있는 **이름 있는** 다른 상품은 그대로 둔다(같은 광고 안의 다른 상품일 수 있음). 의미 단계 기록 `merge_rules`.

**R3(관측 대상 규칙 `unnamed-target-rules/2`).** 이름도 상품명·유형(`*.name`·`*.type`) 근거도 없이 영역 하나의 문구만 근거로 생긴
대상은, 같은 관측에 이름 있는 대상이 하나뿐이면 그 대상에 합친다. whole-test 적립식 광고 2(w052): 적금 유의사항('이 예금은
예금자보호법에 따라…')을 퇴직연금 유의 특징으로 인용한 이름 없는 대상이 그 유의사항 영역을 가져가 퇴직연금 템플릿이 붙었다.

**저장 응답 재적용**(whole-test 102개, 관측·통합 응답 그대로 + 새 규칙, 모델 호출 없음): 템플릿 정답 81 → **83**/84, 부분 3 → 1,
정답→오답 0. 해결 w042·w052. 남은 부분 w061: 첫 입력(1번 이미지)이 '저축예금'을 거치식으로 잘못 판정했고 규칙대로 유지된다.
상품 수가 준 묶음: w023 3→1, w030 2→1, w062 3→1, w069 4→2, w073 4→2(템플릿은 그대로 정답).

**이미지만으로 템플릿 판정(제안 검토).** 이미지만 주면 근거 인용 검증(할루시네이션 방지)과 작은 글씨 결정 신호(대출모집인 등록번호 등)를
잃고 HWP·긴 문서에 약하다. 이번에는 텍스트 노이즈로 생기는 대상을 코드 규칙(R3)으로 막았다. '이미지로 상품·템플릿을 먼저 정하고
텍스트는 영역 배정에만' 쓰는 방식은 별도 비교 실험 대상으로 남긴다.

## 4. HWP 구조 경로(hwp-structure/1) — 기존 parser-pipeline 경로 이식

기존 parser-pipeline 의 HWP 처리 코드를 그대로 옮겼다(`layout_pipeline/hwp_legacy/`, 출처 nh-ad-compliance dev 186ddca:
`ingest/hwp_render·hwp_html·hwp_layers·hwp_pagination·hwp_drawings.py` 파일 그대로, `run.py` 108-325행 hybrid 함수 본문 그대로).

| 단계 | 기존 parser-pipeline | 이 파이프라인 |
|---|---|---|
| 변환 | document-processor HTML → Chromium PDF + DOM 행 | 같은 코드(hwp_legacy). 사내 패키지가 있는 가상환경(PN_HWP_PYTHON)에서 별도 프로세스, ASCII 정션 |
| 영역 | DOM 행 → 구조 Region(`dom_rows_to_blocks`), 3개 이상이면 hybrid | 같은 함수. Stage 1 이 구조 Region + 남은 시각 Region 으로 영역을 만든다 |
| 시각 블록 | PaddleX parsing 블록 중 구조에 없는 것(`_novel_visual_blocks`·`_attach_visual_supplements`) | 같은 함수. 블록 = 레이아웃 검출 영역, 문구 = 중심이 그 안에 든 OCR 줄 |
| 문구 | 구조 Region = HWP 원문(DOM 행). 시각 Region = OCR/VLM | 구조 Region = HWP 원문(VLM 판독 없음). 시각 Region = 기존 VLM 판독 |
| 템플릿·배정·라벨 | 기존 P2/P3 | 이 파이프라인 의미 단계 그대로 |

결과 표시: 구조 Region ID `…-h0-H###`, `read_path: hwp_structure`, 맥락 사유 `hwp_structure_text`, 표 행은 셀 구조
(`table.structure: hwp-dom-row/1`, 1행). OCR 대조 불일치는 `ocr_hwp_mismatch`(원문과 렌더 OCR 차이). 페이지 이슈 `HWP_STRUCTURE_REGIONS`.
변환기의 DOM 행은 `pages/hwp/<file_id>.dom_rows.json`(DOM 행 기록이 없는 이전 변환은 다시 변환).

옮기지 않은 것: 렌더 PDF 텍스트층(triage·pdf_geometry)과 원본 구조 줄(hwp_structure·Kordoc)로 표 행 안 새 문구를 보태는 부분.
