# 15. 상품 목록을 먼저 확정하는 의미 단계(inventory-first)

기준일 2026-10-27. docs/14(의미 단계 legacy: 관측·통합)의 5·6단계를 바꾼 기록이다. 파싱(layout-result/2)·라벨링(label/3)·검사는 그대로다.

> **정정(2026-10-28, docs/16)**: inventory/3 부터 상품 목록 프롬프트의 [이미지] 줄이 깨져 있었다(작성자 버그). §5 의 E8–E10 과 §6 test-tmp 의
> 상품 목록 호출은 모두 이 상태다. 같은 요청 반복 진단에서 버그를 고쳐도 상품 수 결과는 비슷했고, 상품 목록 호출은 같은 요청에도 결과가 갈렸다.
> 사용자가 확인한 test-tmp 오류(tt02·tt03 상품 누락, tt05 초과)와 원인 분석은 docs/16 에 있다.

## 1. 바꾼 이유

legacy(observe/7·integrate/4)는 관측 호출 하나가 **상품 목록과 영역별 소속을 같은 응답에** 낸다. 작은 묶음(4쪽·80영역·16,000자·이미지 6장
이하)은 묶음 전체를 한 번에, 그보다 크면 **페이지마다 따로** 상품을 찾은 뒤 통합 호출이 페이지별 상품을 잇는다(페이지마다 대상 1개 이상 필수).
상품 수를 먼저 확정하는 단계가 없다.

`final-2026-10-27-v2` 기록 집계(개발·회귀 자료):

- 상품이 1개로 정해진 11묶음 273영역은 모두 그 상품에 배정됐다. 오류는 **상품 수 자체**에서 났다.
- 상품 수·연결이 틀린 묶음 5/18: g01 대출 포스터 2(이름 없는 대출 상품 추가), g06 청년미래적금 4파일 3(f08+f11 / f09 / f10), t07 연금-05
  4(라인업의 정기예금·GIC·ELB), t09 연금-07 2, tmp 광고 9개 묶음 30(페이지 후보 31개를 통합이 거의 그대로 둠). g06·t07·tmp 는 페이지별 관측 묶음이다.
- **정정**: docs/14 §6.2 와 이전 완료 보고의 "청년미래적금 4파일이 같은 product_id"는 최종 실행(final-2026-10-27-v2)에서 사실이 아니다(3개로
  갈림, 통합 응답 sem-0022). 이전 파일별 비교 스크립트가 파일 사이 상품 동일성을 보지 않아 놓쳤다. 이번부터 묶음 단위 상품 수·파일 연결을 함께 본다.

## 2. 참고 구현 확인(nh-ad-compliance/parser-pipeline, 읽기만)

- `vlm/client.py::classify()`: 첫 페이지 이미지 + 파일명 힌트(강한 사전확률)로 문서 상품군을 정한다. 파일명·첫 페이지 기준이라 쓰지 않는다.
- `parse/semantic.py::analyze_page_ownership()`: 페이지(긴 페이지는 밴드)마다 한 호출로 상품 목록(product_N)과 영역 소속(product_N·page_common·
  unknown)을 함께 받는다. legacy 와 같은 구조이며 상품 수를 먼저 정하지 않는다.
- `parse/pipeline.py::run_full_pipeline()` + `_known_products_block`·`merge_known_products`: 페이지를 순서대로 처리하며 앞 페이지에서 찾은
  상품을 다음 페이지 프롬프트에 넘겨 같은 ID 를 쓰게 한다. "휴대폰 화면·웹 캡처가 여러 개라도 화면 하나가 상품 하나는 아니다. 상품명이나 종류가
  다를 때만 다른 상품" 지시를 둔다. 그쪽 문서에도 같은 과분리 사례(5쪽 입출식 광고가 화면 열마다 상품 3개)와 실행마다 결과가 흔들리는 문제가 있다.
- 가져온 것: 상품 ID 를 묶음 전체에서 고정, 화면·탭·캡처는 상품이 아님, 새 상품은 이름·종류가 다를 때만. 가져오지 않은 것: 파일명 힌트,
  첫 페이지 기준, 앞 페이지 판단에 기대는 순차 처리.

## 3. 처리 순서(inventory-first, `--classification-mode` 기본값)

코드: `layout_pipeline/product_inventory.py`(분류·배정·퇴직연금 확인), `semantic.py`(실행·trace·검사), 라벨링 `labeling.py`(그대로).

1. **상품 목록(inventory, 묶음당 1회)**
   - 입력: 묶음의 모든 파일·페이지 최종 text·표 rows(생략 없음) + 이미지. 묶음 전체 이미지(페이지·긴 이미지 구간)가 6장 이하면 영역 번호를
     그린 페이지, 넘으면 모든 페이지·구간을 6칸씩 모은 축소 개요. 파일명·file_id·submission_id 없음(중립 별칭 F1·P1·P1-R01).
   - 응답: 헷갈리는 언급(mentions, 역할) → 상품 목록(이름·상품군·템플릿·근거 인용) → 페이지별 상품 연결. **영역 배정은 받지 않는다.**
   - 코드 검사: 인용이 그 영역 text·표 셀에 통째로 있어야 근거로 인정. 이름도 유효 근거도 없는 대상은 버린다. 상품의 페이지 = 응답의 페이지
     연결 ∪ 유효 근거가 있는 페이지(연결 누락으로 다른 상품 페이지에 조용히 배정되지 않게).
   - 입력 상한 140,000자(2026-10-27 확인 호출에서 서버가 약 9.6만 토큰 요청을 처리). 넘으면 문구를 잘라 보내지 않고 그 묶음을
     `inventory_input_too_large` 실패로 둔다(페이지별 상품 찾기로 돌아가지 않음). 가장 큰 tmp 묶음(9파일 18쪽)이 약 6.9만 자.
2. **영역 배정(assign, 필요한 페이지만)**
   - 페이지의 후보 상품 = 그 페이지에 연결된 상품. 연결이 없으면 같은 파일의 상품. 같은 파일에도 상품이 없으면 미확정
     (`page_without_product`). 묶음의 다른 파일 상품에는 넣지 않는다(E7·E9: 상품 목록이 놓친 광고의 영역이 다른 상품에 배정됨).
   - 후보가 1개면 **호출 없이** 모든 영역을 그 상품에(`basis=single_product`, `scope=specific`).
   - 후보가 2개 이상인 페이지만 모델 호출(`basis=model`). 응답 스키마는 그 페이지 후보 상품 번호만 허용한다(새 상품 필드 없음).
     specific·shared·mixed(상품별 인용)·unknown. 긴 페이지 이미지가 6장을 넘으면 구간 묶음별로 나눈다.
   - 상품이 하나도 없으면 영역은 `partial`·`no_advertised_product`(억지로 만들지 않음).
   - 상품 목록 호출이 페이지 연결에 목록에 없는 대상 번호를 쓰면 무시하고 trace 오류로 남긴다.
3. **퇴직연금 운용상품 확인(pension-scan, 퇴직연금 상품마다 1회, 텍스트만)**
   - 그 상품이 걸친 파일의 모든 영역 문구에서 분류 정책의 퇴직연금 특징(제도·운용상품·원리금보장·일반 고지)에 해당하는 인용만 찾는다.
   - 포함·미노출·미확정은 인용 검증된 근거와 페이지 처리 상태로 코드가 정한다(classify._pension). 확인 호출이 실패하면 미노출이 아니라
     미확정(`pension_scan_failed`).
4. **라벨링(label/3)**: 상품 템플릿의 라벨 스키마로 상품별·영역 묶음별(병렬). 그대로.
5. **검사·출력**: 계약·참조·보존·라벨 인용 위치 검사, 파일별 layout-result/3, 결과 화면, 입력 검토 화면(report.html).

GPU 동시 호출 상한(기본 2)은 의미 단계의 모든 호출이 함께 쓴다. legacy 모드(`--classification-mode legacy`)는 이전 결과 재구성·비교용으로 남겼다.

## 4. 최종 JSON(layout-result/3 확정, 2026-10-27 사용자 확인)

입력 파일마다 `files/<file_id>/result.json`. 같은 묶음의 여러 파일은 같은 product_id 와 같은 상품 정의를 담는다.

```
layout-result/3
├ contract, result_id, submission_id
├ source        파일 정보(file_id·파일명·입력 순서·형식·해시·페이지 수)
├ parse         근거 파싱 결과(layout-result/2) id·경로
├ semantic      profile, classification_mode(inventory-first|legacy), status(completed|partial|failed), versions
├ pages[]       파싱 결과 그대로(이미지 경로만 새 위치 기준)
├ products[]    product_id, name(원문 상품명, 없으면 null), product_group, status(classified|undetermined|unsupported)
│               templates[{template_id, role(product|component), label_schema}]
│               pension{investment_products, plans, components} | null
│               files[], pages[](상품이 걸친 페이지, 다른 파일 포함), review{required, codes}
├ regions[]     파싱 필드 그대로 + product_assignment{status, scope, product_ids, basis}
│               + labeling{status, items[{product_id, label_ids}]} + semantic_review{required, codes}
├ unassigned_texts[]  그대로
└ trace_ref     파싱 결과·의미 단계 trace 경로
```

- 추가: `semantic.classification_mode`, `products[].pages`, `product_assignment.basis`(single_product | model | null).
- 결정(사용자 확인): 아직 배포 전이라 layout-result/3 을 이 구조로 확정한다. 이전 실험 출력(final-2026-10-27-v2 등)은 초안 /3 이다.
  라벨 근거 인용·특징 ID·프롬프트·응답은 trace 에만 둔다.
- 계약 검사 추가: basis 와 상태·scope 일치(스키마), 상품 pages 가 배정 영역 페이지를 모두 포함, 묶음의 페이지만, files = pages 의 파일.

## 8. 남은 문제와 결정할 것

- **한 페이지 두 상품 누락**(g07·tt02·tt03, g08 은 실행마다 다름): '상품 목록 먼저'의 약점이다. 영역을 하나씩 보지 않으니 두 번째 상품을 놓친다.
- **하위 항목의 독립 상품화**: 범위 밖 상품(NH포인트 배너, 마이너스통장 약정 방식)이 실행에 따라 생긴다. 그 상품 영역은 라벨링하지 않는다.
- **여러 광고를 한 번에 올린 묶음(tmp)**: 7·1개로 크게 흔들린다. 한 요청(약 5만 토큰)에서 광고 9개를 안정적으로 세지 못한다.
- **n01**(이름 없는 입출식 우대 조건 화면): 템플릿 미확정. legacy 는 입출식.
- legacy 의 약점은 그대로다: 페이지별 관측 묶음(g06·t07·tmp)의 과분리, 단일 요청에서도 g01·t09 의 추가 상품.

1. **크기별 혼합(권장)**: 한 요청에 들어가는 작은 묶음은 legacy 관측(상품 목록과 영역 배정을 한 번에, 모든 영역을 보며 상품을 셈) +
