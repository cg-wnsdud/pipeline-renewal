# 18. 심의 단계 입력(review-input/1)·문구 순서 오류 원인(2026-10-28)

## 1. 심의 단계 입력

최종 결과(layout-result/3, 파일별)는 실행·버전·경계·진단·근거까지 담아 심의 단계에 바로 넘기기 어렵다. 묶음(submission) 하나마다 심의에 필요한
값만 추린 JSON 을 `<out>/semantic/handoff/<submission_id>.json`(`layout_pipeline/handoff.py`)으로 더 만든다. 구조는 README "심의 단계 입력".

- nh-ad-compliance 는 한 광고의 여러 파일을 한 번에 올리고 파서를 묶음 단위로 한 번 부른다(`parse_group`). 그래서 묶음 하나 = JSON 하나다.
- 값은 layout-result/3 그대로 옮긴다. `handoff/check.json` 이 영역 집합·bbox·text 보존과 상품·라벨 참조를 검사한다.
- 기존 parser-pipeline 출력(P3 `nh-ad-region-review-input-v11` + P1 `nh-ad-parse-evidence-v6`)과 다른 점(사용자 결정: 우리 구조 기준):

| 항목 | 기존 P3 | review-input/1 |
|---|---|---|
| 영역 ID | 페이지별 `pN_rNNN` 로 다시 매김 | layout-result/3 의 region_id 그대로 |
| 표 | `selected_text` 를 GFM 마크다운으로 바꾸고 `table.cells`(row_span·col_span·is_header) | `text` 는 판독 문구 그대로, `table` 은 셀 구조(n_rows·n_cols·cells[rowspan·colspan]). 머리글 여부 없음 |
| 상품 소속 | `product_id` 하나(`product_N`·`page_common`·`unknown`) | `scope` + `product_ids`(여러 상품 공통·혼합 영역 표현) |
| 라벨 | 영역당 목록 하나 | 상품별 `label_ids` |
| 템플릿 | 문서 수준 `document.template`(사용자 지정이면 `source=user_provided`) | 상품별 `templates[].labels` |
| 묶음 페이지 | `page_no` 를 묶음 전체로 다시 매기고 `source_file`·`source_page_no` | `page_id`·`file_id`·파일 안 `page_no` |
| 짝 근거 파일 | P1(OCR 줄·원래 영역 ID, 판정 엔진이 읽음) | 만들지 않음 |

parser-pipeline 을 이 파이프라인으로 바꿀 때 심의 쪽(worker `rule_judge.py`·`nh_parser.py` 의 계약 버전 검사, rule-engine `inputs.py`·`chunking.py`·
`source_binding.py`·`reading_quality.py`, backend `operational*.py`)이 위 차이를 받도록 맞춰야 한다. 사용자가 등록 때 고른 템플릿을 의미 단계에 넘기는 입력도
아직 없다.

## 2. 문구 순서 오류 원인(e2e-2026-10-28)

**요약**

- 증상: VLM 이 쓴 영역 최종 문구의 줄 순서가 원본과 섞이거나(tp02 S004, tp01 t4-L006) 같은 줄이 중복된다(tp06 L002).
- 원인: VLM 에 참고로 주는 OCR 후보 목록을 문자열 순으로 정렬해 주는데(OCR 순서를 베끼지 않게 하려는 docs/04 설계), VLM 이 이미지 대신 그
  목록 순서를 따라 쓰는 경우가 있다. 목록을 위치 순으로 바꾸면 이번에는 항목명–값 2단 배치에서 줄이 번갈아 섞인다. 어느 순서든 목록을 따라가는
  경향이 근본 원인이다.
- 남은 이유: (1) 순서 검사는 표시만 하고, 보충 영역은 재판독 단계가 없다 (2) 순서 검사는 한 단 배치만, OCR 문자열이 정확히 같을 때만 위치를
  찾는다(tp01 L006 놓침) (3) 표 셀 재판독이 구조 검사에 실패하면 맞는 문구까지 버리고 중복 있는 1차 판독으로 돌아간다(tp06).
- 원인이 아닌 것: OCR 문자열 조합(코드가 OCR 로 문구를 만들지 않음), 레이아웃 누락 자체(S004 상자는 정확했고 섞임은 VLM 판독에서 생김).

공통 원인: OCR 후보를 VLM 에 **문자열 순으로 정렬해** 준다(`vlm_tasks.candidate_context`, crop/2·3 과 page/2 가 같이 씀). OCR 배열 순서를 읽기
순서로 베끼지 않게 하려는 설계(docs/04)인데, 모델이 정렬된 순서를 따라 쓰는 경우가 있다.

### tp02 `t2-S004` 문장 순서가 섞임

1. 레이아웃 모델이 이 블록(이자지급 방법 본문·※ 각주)을 상자로 내지 않아 OCR 줄 6개가 모두 미배정 → 놓친 영역 보충이 OCR 묶음으로 S004 를 만들었다.
2. 보충 영역은 crop 묶음 판독(crop/3, 7영역 한 요청, `vlm-0009`)으로 읽는다. 넘긴 후보 순서가 `※예금의…`·`날부터는…`·`매년 3월…`·`있습니다.`·
   `직전 영업일…`·`추가 입출금…`(가나다순)이고, 출력은 이 순서와 거의 같다(`있습니다.` 만 끝으로). 원본 순서는 `매년…`→`직전…`→`※예금의…`→`날부터…`
   →`추가…`→`있습니다.` 다.
3. 순서 검사(simple-column-order/1)가 역전 1건을 찾아 `reading_order_conflict` 를 붙였지만, **보충 영역에는 재판독 단계가 없어** 그대로 남았다.

### tp06 `L002` "(직전 분기 수수료무료)" 가 위아래 두 번

1. OCR 에는 이 문구가 표 아래에 한 번만 있다. 후보 정렬에서 '(' 가 한글보다 앞이라 후보 목록 **맨 앞**에 왔고, 1차 페이지 판독(page/2, `vlm-0001`)이
   영역 문구 맨 앞에 한 번 쓰고 원래 위치(맨 끝)에도 썼다.
2. 검사가 반복(`repeated_text_in_page_read`)과 표 행 불완전을 잡아 표 셀 재판독(table-cells/1, `vlm-0003`)을 보냈고, 재판독 문구에는 한 번만 있었다.
3. 재판독 셀 구조가 계약 검사에 실패했다(`n_rows=8` 인데 9번째 행 셀 4개, (4,2)~(4,4) 빈 칸). 표 판독은 "부분 응답을 섞지 않는다" 규칙이라 재판독 전체를
   버리고 1차 페이지 판독(중복 포함)을 남겼다. 결과에 `repeated_text`·`table_structure_failed` 검토 표시가 있다.

## 3. 수정 비교(2026-10-28)

세 수정을 실행 옵션으로 넣고(기본값은 이전 동작) 같은 Stage 1 로 비교했다. 실행 폴더 `work/pipeline/fixcmp-2026-10-28`, 스크립트
`work/run-fixcmp-2026-10-28.sh`·`work/run-fixcmp-rep-2026-10-28.sh`. 의미 단계는 끔. 공유 GPU, 동시 2.

| 옵션 | 내용 |
|---|---|
| `--ocr-candidate-order position` | OCR 후보를 위치 순(위→아래, 같은 줄 왼쪽→오른쪽)으로 주고 프롬프트의 순서 설명도 바꾼다(`vlm_tasks.position_order`·`order_prompt`, 요청 meta `candidate_order`) |
| `--supplement-reread` | 보충 문자 영역도 본 판독의 영역 확인 조건(작은 글자 조건 제외)에 걸리면 region-reread/1 로 재판독하고 같은 선택 정책으로 고른다 |
| `--table-text-fallback` | 표 셀 재판독이 셀 구조만 실패하고 문구는 온전하면 그 문구를 쓰고 표는 `structure=text-only`(rows·cells 없음) |

### 3.1 보고된 오류 재현(tp02·tp06 반복)

| 오류 | 기존(문자열 순, 4회: 오전 e2e + 3회) | 수정(세 옵션, 3회) |
|---|---|---|
| tp06 L002 문구 중복 | 4/4 중복(매번 1차 페이지 판독에서 생김) | 0/3(1차 페이지 판독부터 중복 없음) |
| tp02 S004 줄 섞임 | 영역이 생긴 3회 중 1회(1회는 보충 후보가 버려져 영역 없음) | 0/3 |

tp06 L002 의 표 셀 재판독은 두 조건 모두 매번 셀 구조 검사에 실패했다(표 안의 표). 수정 조건에서는 text_fallback 으로 재판독 문구를 썼고, 이 문구는
병합 칸 'A형 / B형' 을 한 번만 쓰고 'NH밸런스' 를 맞게 읽었지만 줄바꿈이 없고 '(분기별 후취' 의 닫는 괄호가 빠졌다.

### 3.2 12개 입력 전체(e2e 12개, 각 1회)

- 영역 446개. 같은 코드 두 실행(오전 e2e ↔ 기존 재실행)과 기존 ↔ 수정 모두 정규화 문구 같은 영역 415/446. 전체 지표(품질 사유 수, OCR 덮임 평균)로는
  수정 효과와 실행 변동을 구분할 수 없다.
- 보충 재판독은 이 실행에서 조건에 걸린 보충 영역이 없어 0회. 표 문구 대체는 2회.
- 기존 ↔ 수정에서 문구가 달라진 31개 중 원본 이미지와 대조한 것:

| 결과 | 영역 |
|---|---|
| 수정이 맞음 | tt02 L000(제목 블록 순서), tt02 L012(• 줄이 ①②③ 앞), tp07 L015('수익률 이륙, NH농협은행과…'), tt02 L005('⑦번동의서'), tp06 L002 |
| 수정이 틀림 | tp03_p02 L022·tt03 L007(왼쪽 항목명 2줄–오른쪽 값 2줄 배치에서 항목명 줄과 값 줄을 번갈아 씀), tt03 L003(단어마다 줄바꿈, 위치 순 후보 목록을 옮겨 쓴 형태) |

### 3.3 판단

- 위치 순 후보는 보고된 두 오류를 없애고 순서 오류 몇 개를 고쳤지만, 항목명–값이 좌우로 놓인 배치에서 줄을 섞는 회귀가 있다(docs/04 에서 순서를 감춘
  원래 이유). 이대로 기본값으로 바꾸지 않는다. 다음 후보: 위치 순이되 열(블록) 단위로 묶고(왼쪽 열 줄을 모두 쓴 뒤 오른쪽 열), 같은 줄의 단어 상자를 한
  후보로 합치는 표현(position/2).
- 보충 재판독은 확인 조건에 걸린 보충 영역에만 동작한다. 이번 실행에서는 0회라 실측 근거가 없다(단위 테스트만).
- 표 문구 대체는 셀 구조 실패 때 중복 1차 판독 대신 재판독 문구를 쓰지만, 그 문구는 줄바꿈 없는 형식이다. 2회뿐이라 판단을 미룬다.
- 기본값은 세 옵션 모두 이전 동작 그대로 둔다.

## 4. 실험: OCR 줄 번호 순서 방식(line-order/0, tp02·tp06)

문구를 VLM 이 자유롭게 쓰는 대신, OCR 줄마다 번호 상자를 그린 사본을 보여 주고 VLM 이 ① 읽기 순서(줄 번호 순열) ② 이미지와 다른 줄만 교정
③ 그림을 읽은 줄 제외 ④ OCR 이 놓친 글자를 낸다. 코드는 순열·참조를 검사하고 정해진 순서로 줄을 잇는다. 파이프라인에는 넣지 않은 실험이다
(`work/experiments/line_order_probe.py`, 결과 `work/pipeline/lineorder-2026-10-28`). 영역마다 1회(원본 crop + 번호 사본), 동시 2.

| 항목 | 결과 |
|---|---|
| 계약(모든 줄 번호를 order·drop 에 정확히 한 번) | 67/67 영역 통과 |
| tp02 S004 | 순서 맞음, OCR 오독 '공유일'→'공휴일' 교정 |
| tp06 L002 | 중복 없음, 왼쪽 항목명 '수수료' 를 값 앞에 둠, '벨런스'→'밸런스'·'연간보수을'→'연간 보수율' 교정. 각주 줄은 OCR 의 붙은 띄어쓰기·빠진 마침표가 그대로 |
| 기존 결과(4회)와 공백 무시 비교 | 67개 중 60개가 기존 한 회 이상과 같음 |
| 새 문제 | tp02 t0-L004: 4번 줄 교정에 3번 줄 문구를 끌어와 '공공마이데이터' 중복(교정 검사가 '다른 줄 문구 유입'을 보지 않음). tp06 S000: OCR 이 못 찾은 '농협은행 > ISA > 일임형ISA 일임형ISA란?' 을 VLM 이 missing 으로 내지 않아 빠짐 |
| OCR 그대로 쓴 줄 | 180줄 중 107줄. 공백만 기존 결과와 다른 영역 9개(OCR 의 붙은 띄어쓰기 잔존) |
| 비용(이 실험 형태) | tp02 47회·375초·프롬프트 13만 토큰(기존 판독 8회·108초·3.7만), tp06 20회·168초(기존 11회·144초). 영역마다 1회라 호출이 많다. 운영형은 페이지·타일 단위로 묶어야 한다 |

판단: 보고된 순서·중복 오류는 구조적으로 해결되고 교정도 대부분 맞았지만, (1) 교정이 다른 줄 문구를 끌어오는 경우 (2) OCR 이 놓친 글자 누락
(3) OCR 띄어쓰기 오류 잔존이 새로 생긴다. (1)은 '교정 줄에 다른 줄 문구 포함 금지' 검사로 막을 수 있고, (2)·(3)은 기존 방식(VLM 자유 판독)과 교차 확인이
필요하다.
