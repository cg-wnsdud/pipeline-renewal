# 23. 상품 배정 흔들림(layout-order/1 + mixed-check/1)과 2열 라벨-값 영역 판독 분석(2026-10-29)

docs/22 판정 비교에서 나온 두 문제를 분석했다. (1) mx1306 적금 단의 우대금리표가 실행마다 통장·적금으로 배정이 바뀐다.
(2) 왼쪽 라벨 2줄·오른쪽 값 2줄인 짧은 영역(중도해지 및 만기후 금리)을 실행마다 다른 순서로 읽는다.

공통 사실: 같은 이미지·지시문·스키마(바이트 단위로 같음, 온도 0)를 보내도 모델 서버의 응답이 실행마다 다르다(mx1306 페이지 판독
세 번 모두 입력 해시가 같고 출력이 다름). 따라서 결과를 고정하려면 정답이 판단 경계 근처에 있지 않게 입력을 만들어야 한다.

## 1. 상품 배정

### 1.1 지금 방식

의미 단계 관측(observe) 한 호출이 상품·템플릿과 모든 영역의 소속을 함께 정한다. 입력은 영역 상자와 번호(R01…)를 그린 페이지
이미지, 영역 목록(별칭·bbox·최종 문구·표 행), 템플릿 기준이다. 영역마다 scope(specific·shared·mixed·unknown)와 대상을 받는다.

### 1.2 원인

mx1306 은 왼쪽 단 통장(x 230~870)·오른쪽 단 적금(x 950~1580) 2단 광고다. 우대금리표(L005)는 오른쪽 단에 있다.

- **영역 순서**: 영역 목록과 R 번호를 위→아래(같은 줄은 왼쪽→오른쪽)로 정렬해 두 단이 번갈아 나온다. L005 가 통장 단 영역
  R11·R13·R14 사이(R12)에 놓였고, 응답은 R11~R14 를 이어서 통장으로 썼다.
- **문구 속 다른 상품 이름**: 표 첫 행이 '「NH올원e통장」에서 출금하여 신규 시'(적금 우대조건)다. 혼합으로 낸 응답은 모두 이 문구를
  통장 몫으로 인용했다.
- **배치 판단 단계 없음**: 응답이 대상 목록 다음 바로 영역 배정이다(기존 파서는 analysis 를 먼저 받았다). 배치 칸을 더하는 시안은
  나아지지 않아 기각했다(§1.5).
- **이미지**: 1.2MP 로 줄여(921×1303) 보냈지만 서버가 258만 픽셀(1344×1872)로 다시 키운다. 토큰은 같고 번호·글자만 흐렸다.

### 1.3 기존 parser-pipeline 과 차이

| | 기존(nh-parser-fin `parse/semantic.py`, `parse/pipeline.py`) | 이전 layout-pipeline |
|---|---|---|
| 호출 | 페이지마다 1회(긴 페이지는 띠 2~4개), 상품 정의 + 영역 소유권 + 복구 후보 처리 | 묶음(작으면) 1회, 대상 + 템플릿 + 영역 배정 |
| 영역 순서 | 엔진(PaddleX) 순서 유지. 주석: '전체 y 정렬은 2단 문서의 좌우 열을 교차시키므로 사용하지 않는다' | 위→아래 정렬 |
| 응답 | `analysis`(세 문장 이내)를 먼저 쓰고 영역마다 product_N·page_common·unknown + confidence. 상품은 '시각적 순서대로' | 대상 → 언급 → 영역 배정 |
| 이미지 | 상자 그린 원본, 최대 1400×2400 | 1.2MP |

OCR 서버 응답에는 상자(`layout_det_res.boxes`, 우리 영역의 출처)와 별도로 단·구역을 고려한 블록 순서(`parsing_res_list`)가 있고
stage1 기록에 `server_blocks` 로 저장돼 있었다(비교용). mx1306 에서 이 순서는 통장 단 1~10 → 적금 단 11~15(표 포함) → 공통이다.

### 1.4 수정(호출 수 변화 없음)

1. **layout-order/1** (`classify.layout_order`): 관측 요청의 영역 순서·R 번호를 stage1 `server_blocks` 순서로 둔다(같은 뷰에서 bbox
   IoU ≥ 0.7 로 대응). HWP 구조 영역이 있으면 원문(H 번호) 순서가 기준이다. 대응 블록이 없는 영역(놓친 영역 보충, HWP 페이지의 그림
   속 글자)은 가장 가까운 기준 영역 바로 뒤에 둔다. stage1 기록이 없으면(내보낸 결과만) 이전 순서(`position`). 페이지별 기준은
   묶음 정보 `order`(server_blocks·hwp_structure·position), 결과 `semantic.versions.region_order`.
2. **이미지**: 관측 이미지 상한을 서버 기준(`SERVER_PIXEL_BUDGET`)으로 올렸다. 프롬프트 토큰이 같음을 확인했다(V0·V1 같은 입력 5,609~5,625).
3. **mixed-check/1** (`classify.mixed_by_neighbors`, 관측 응답 검사): mixed 는 대상마다 그 영역 인용(parts)이 있어야 한다. 유효한
   인용이 있는 대상이 둘 미만인 mixed 는 레이아웃 순서의 바로 앞·뒤 영역이 같은 한 대상의 specific 이고 그 대상이 이 영역의 대상이면
   그 대상의 specific 으로 둔다(검토 메모 `mixed_unsupported_layout_neighbors`, trace). 위→아래 순서 페이지에는 쓰지 않는다. 그 밖의
   mixed 는 그대로 두고 상품 확정에서 `mixed_parts_missing` 을 붙인다(이전과 같음).
4. 관측 지시(observe/7)는 바꾸지 않았다. 시안 두 개(아래 V2·V3)를 기각했다.

기록: `semantic.versions.region_order = layout-order/1`, `semantic.versions.mixed_check = mixed-check/1`. 영역 순서가 바뀌면 R 번호가
바뀌므로 이전 실행의 저장 응답 재구성(rebuild)은 이 버전 이전 코드로 해야 한다(관측 지시가 바뀔 때와 같다).

## 2. 2열 라벨-값 영역 판독(분석)

대상 영역 mx1306 L017: 왼쪽 파란 라벨 '중도해지 및 / 만기후 금리', 오른쪽 값 '가입일(만기일) 당시 고시된 중도해지 및 / 만기 후 금리 준용'.

### 2.1 어디서 읽는가

페이지 판독(page/2) 한 호출이 이 페이지의 영역 22개를 함께 읽는다. 입력은 원본 페이지(1654×2339, 서버에서 1344×1872 로 줄임)와
상자 표시 사본, 영역마다 bbox 와 OCR 후보다. 이 영역은 1차 판독만 했고(N0·N1·N3), N2 만 순서 검사에 걸려 영역 crop 재판독을 했다.

| 실행 | 최종 문구 |
|---|---|
| N0 | 만기후 금리 중도해지 및 가입일(만기일)당시 고시된 중도해지 및 / 만기 후 금리 준용 |
| N1 | 중도해지 및 만기후 금리 / 만기 후 금리 준용 / 가입일(만기일) 당시 고시된 중도해지 및 |
| N2 | 중도해지 및 만기후 금리 만기 후 금리 준용 / 중도해지 및 가입일(만기일)당시 고시된 중도해지 및(재판독은 맞았지만 채택 안 됨) |
| N3 | 중도해지 및 만기일(만기일) 당시 고시된 중도해지 및 / 만기 후 금리 만기 후 금리 준용(글자도 틀림) |

### 2.2 원인

1. **OCR 줄이 두 열을 한 줄로 묶는다.** 라벨과 값이 같은 기준선에 있어 OCR 글자 검출이 '중도해지 및 가입일(만기일)당시 고시된
   중도해지 및', '만기후 금리 만기 후 금리 준용' 두 줄로 읽었다. 각 OCR 줄이 라벨 한 줄 + 값 한 줄이다.
2. **판독 지시와 OCR 후보가 서로 다른 순서를 가리킨다.** 지시는 '항목명이 여러 줄이면 모두 이어 하나의 항목명으로 쓴 다음 그 값,
   항목명 줄과 값 줄을 번갈아 섞지 않음'(열 단위)인데, OCR 후보는 행 단위로 섞인 줄이고 문자열 순으로 정렬돼 '만기후…' 가 먼저
   온다(N0 은 그 순서로 시작). 작은 글자(1344 폭 축소 페이지의 22개 영역 중 하나)에서 모델이 두 신호를 섞어 실행마다 다르게 쓴다.
3. **검사가 이 배치를 못 본다.**
   - 순서 검사(simple-column-order/1)는 OCR 줄이 판독 문구에 그대로 들어 있을 때만 위치를 잡는다. 열 단위로 바르게(또는 다르게)
     쓰면 행 단위 OCR 줄이 문구에 그대로 없어 검사가 비고, OCR 줄을 거꾸로 베낀 N2 만 걸렸다.
   - OCR↔VLM 대조는 일부러 순서와 무관한 어절 단위라 순서 오류를 잡지 않는다. N3 의 '가입일→만기일' 한 글자 차이와 겹친 어절도
     문턱 안이었다.
4. **바르게 읽은 재판독을 버린다.** N2 재판독(원본 crop)은 '중도해지 및 / 만기후 금리 / 가입일(만기일) 당시 고시된 중도해지 및 /
   만기 후 금리 준용' 으로 맞았다. 재판독 선택 규칙(reread-select/2)은 OCR 줄이 문구에 덮이는 비율이 1차보다 크게 낮으면(1.0 →
   0.714) 충돌로 보고 1차를 남긴다. OCR 줄이 행 단위로 두 열을 묶고 있어 열 단위로 바른 문구일수록 이 비율이 낮다.

즉 근본 원인은 OCR 한 줄을 읽기 단위로 쓰는 곳(판독 후보·순서 검사·재판독 선택)이 두 열을 묶은 OCR 줄을 그대로 믿는 데 있다.
같은 입력에도 출력이 달라지는 서버 특성이 이 모호함을 실행마다 다른 결과로 드러낸다.

### 2.3 고칠 방향(이번에는 하지 않음)

- 재판독 선택의 충돌 판단을 순서와 무관한 글자 덮임으로 바꾼다(N2 의 바른 재판독 채택).
- 1차 판독 문구에 OCR 줄이 하나도 그대로 없는데 어절 대조는 높은 영역(순서를 바꿔 쓴 영역)을 재판독 조건에 더한다(영역 crop 은 이번
  사례에서 맞게 읽었다). 대상이 이런 영역뿐이라 호출 증가는 작다.
- OCR 줄 상자 안에 큰 가로 틈이 있으면(rec_polys 로 확인 가능한지 먼저 확인) 후보를 둘로 나눠 주는 방안.
