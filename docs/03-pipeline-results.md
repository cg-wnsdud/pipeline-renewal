## A. 평가 보완(저장 응답 재평가, 호출 0회)

**바뀐 코드**: `layout_pipeline/text_eval.py`(eval/2 → 2.1), `eval_report.py`(신규), `run_vlm_eval.py`(집계 교체).

**지표를 둘로 나눴다.**
- **정답→출력**:
  - 줄마다 정확(정규화 후 완전 일치) / 근사(줄 길이 10% 이하 편집) / 누락으로 나눈다.
  - 편집거리 합/정답 글자 수는 **'recall 측 편집 비율'**로 이름을 바꿨다. 출력의 추가 글자를 세지 않으므로 표준 CER이나 전체 정확도가 아니다.
- **출력→원본(신규)**:
  - 출력 글자마다 정답 줄의 3글자 조각으로 뒷받침되는지 본다.
  - 영역 안 정답으로 설명되지 않고 페이지 다른 정답으로만 설명되면 **위치 오류**다.
  - 어디에도 없으면 **근거 없는 글자**다. 연속 4자 이상이면 **추가 구간**(환각·오염), 그보다 짧으면 **글자 오류**로 센다.
  - 정답 자체가 빠뜨린 실제 문구가 있을 수 있으므로 오류 '후보'다.
- **페이지 단위(신규)**:
  - 페이지의 모든 정답 줄을 분모로 둔다. 일부 포함·미배정·레이아웃 미검출 줄도 포함한다.
  - 각 줄을 다음 중 하나로 분류한다: 소속 영역 문구 / 경계 영역 / 다른 영역 / 미배정 OCR에만 / 판독 실패 영역 OCR에만 / 누락.
- **eval/2.1**: 시각 구분자 '|'를 정규화에서 제외했다. VLM이 메뉴에 넣은 '|' 때문에 내용이 같은데 누락으로 세던 문제다.

**Codex 반례 확인(테스트 `test_eval_counts_unsupported_additions_and_tokens`)**:
- 정상 문구 뒤에 지어낸 설명을 붙이면 → 근거 없는 글자 ≥10, 추가 구간 1
- 특수 토큰 오염 → 추가 구간
- 다른 영역 문구 → 위치 오류

**저장 응답 재평가**(모델 입력은 그대로):

| 조건 | 정답 줄 정확 / 근사만 / 누락 (165) | recall 측 편집 비율 | 근거 없는 글자 | 추가 구간 | 숫자 누락/추가 |
|---|---|---:|---:|---:|---|
| A 페이지 배치 | 138 / 16 / 11 | 0.116 | 13 | 0 | 19/1 |
| B 영역 crop | 152 / 8 / 5 | 0.013 | 6 | 0 | 3/0 |
| 표 v3(정답 346) | 326 / 7 / 13 | 0.012 | 40 | 2 | 9/1 |

- 이전에 보고한 "B 160/165, CER 1.5%"는 근사 일치를 포함한 수치였다. **정규화 정확 일치는 152/165**다.
- 새 지표가 처음 잡은 실제 오류: f04 표 후보 L003의 예금보험 배지는 원본이 "1인당 최고 **1억원**"인데 VLM 출력은 "**5천만원**"이다(환각, 원본 확대로 확인). 정답 자료에 이 배지 줄이 없어 정답 쪽 지표로는 드러나지 않았다.

## B. 영역 crop 여백 1조건 비교

**사전 고정**
- 여백 규칙 `ocr-median-0.3/1`: `max(4, round(0.3 × 페이지 OCR 상자 높이 중앙값))` px.
  - 페이지별 값: f01 9 / f12_p02 10 / f13 17 / h01 11~15px.
  - 저장 bbox는 그대로 두고, 모델 입력 crop 범위와 crop 안 대상 좌표(`target_in_crop_px`)를 호출 기록에 남긴다.
- 사례: 기존 29영역 + 이웃 혼입 위험 7영역(`fixtures/vlm-margin-added-set.json`). 여백 안에 이웃 영역 정답 문구가 있는 경우다.

**결과**: 호출 15회. 지표는 정확 / 근사만 / 누락 / 위치 오류 순.

## D. 긴 이미지 자동 경계

**코드 수정(오프라인)**: `compose_sequence`를 동적 계획법으로 바꿨다. 길이 상한과 비율(너무 길거나 짧은 타일) 조건을 함께 만족하는 경계열을 찾고, 타일 수 최소 → 최단 타일 최대 순으로 고른다.
- Codex 반례(extent 1000, safe 400·480·750·950, 최대 500, 비율 2.5)에서 합격 경계열을 찾는다.
- 경계열이 없으면 `no_safe_boundary`를 낸다(테스트).

**실험**: 사전 계획은 `docs/boundary-experiment-plan.md`이며 실행 전에 고정했다.

1. 탐색 OCR 12회: 비율 2.5 창, 50% 겹침, f08 7 / f09 3 / f11 2. 기하 후보 69개(f08 39 / f09 19 / f11 11).
2. 라벨 24개: VLM 실행 전에 제가 원본을 보고 고정했다(`fixtures/boundary-labels.json`, 사람 검토 아님). safe 10 / unsafe 14. Codex 음성 대조 f08 1664(버튼, 1668)·4720(제목, 4728)을 포함했다.
3. 판정 방법(VLM 24회, 반복 없음):
   - M1 간격 규칙
   - M2 관계 유형 분류: 코드가 `independent_sections`만 safe로 받는다. 근거 ID 검사 포함.
   - M1∧M2

| 방법 | false-safe(0이어야 통과) | safe 재현율(≥50%) | 판정 |
|---|---|---:|---|
| M1 간격 | 7 | 70% | 미통과 |
| M2 관계 분류 | 6: 요약 카드 내부, **버튼-설명(1664)**, 탭-내용, 목록 항목 2, 표-각주 | 100% | 미통과 |
| M1∧M2 | 5 | 70% | 미통과 |

- **M2가 맞힌 것**: 제목-설명 4건과 배지-설명 2건을 모두 거부했다. Codex 실험에서 반복 오판한 f08 4728 위치도 `heading_and_body`로 맞혔다.
- **M2가 틀린 것**: 버튼-설명, 탭-내용, 목록·표-각주 연결을 '독립 섹션'으로 봤다. 그래서 M2 판정만으로 만든 f08 경계열에는 탭 메뉴와 내용을 가르는 3417이 포함된다.
- **표 내부**: 기하 후보가 하나도 생성되지 않았다. 표가 레이아웃 상자로 검출돼 보호된다.
- **허용 길이보다 긴 연속 영역**: 라벨 기준으로 f09 우대금리 섹션(금리 상자·설명·표·각주, y≈0~2131)에는 안전 경계가 없다. 한도 1640px를 넘으므로 경계열 구성이 `no_safe_boundary`다. 타일 정책 자체(더 긴 타일, 같은 영역 복수 이미지)를 결정해야 하는 사례다.
- **결론**: 자동 의미 경계 **미완료**. 계획은 저장하지 않았고, `validated`·`human_review`를 붙이지 않았다. f08·f09·f11은 대기 상태다.
- **다음 가설 후보(미실행)**: 탭·버튼·목록·각주를 명시적으로 구분하는 관계 정의와 레이아웃 연결 신호(같은 카드 배경·같은 목록 들여쓰기)를 함께 쓰는 방법. 같은 사례 세트에서 1회 비교한다.

## E. 서버 옵션 문제와 동시성

### E1. class별 layoutThreshold dict(별도 관리 항목)

- **확인된 사실**: 기본값과 같은 class별 dict를 보낸 확인 호출 1회(`work/runs/verify-threshold-dict`)에서, h01_p03이 13상자에서 10상자로 줄었다. 점수 0.5 미만 제목 3개가 빠진 것이다.
- **원인(미확정)**: 공개 PaddleX 3.6.1 소스의 int 키 조회와 JSON 문자열 키 불일치 가설과 부합한다. 하지만 **실행 중인 컨테이너 코드는 확인하지 않았다.** 서버를 변경하지 않았다.
- **사용자 확인이 필요한 것**(Codex `server-check-request.md`, 읽기 전용, 수정·재시작 없음):
  1. 실제 설치된 paddlex 버전과 로드되는 코드 경로
  2. 요청 스키마의 layoutThreshold dict 키·값 타입
  3. serving handler → pipeline → predictor → postprocessor 사이에 키를 숫자로 정규화하는 과정이 있는지
  4. 최종 후처리의 threshold 조회 코드, 키 타입, 키가 없을 때의 기본값
  5. layoutMergeBboxesMode dict도 같은지
- **이 정보가 막는 실험은 하나뿐이다**: 웹 레이아웃 누락(미배정 OCR에만 남은 137줄 대부분)을 "표·이미지는 그대로 두고 텍스트류 문턱값만 낮춤" 조건으로 줄이는 비교. 평가·판독·통합 실행은 이 정보 없이 계속했다.

### E2. 동시성(같은 작업량, 각 조건 1회, 공유 GPU)

**측정 조건**
- OCR: 일반 16페이지 전체 입력.
- VLM: `stage1-merge-large`의 200영역 판독(HTTP 50회).
- 처음 측정(cached)은 같은 요청을 반복 실행해 서버 prefix cache 영향을 받았다. 그래서 요청마다 고유 식별자를 프롬프트 맨 앞에 붙이는 `--cache-bust`로 다시 측정했다(아래 VLM 표).
- 다른 사용자의 GPU 부하는 통제하지 않았다.

| 측정 | 동시 1 | 동시 2 | 동시 4 | 혼합(다른 작업과 동시) |
|---|---:|---:|---:|---:|
| OCR 16페이지 벽시계 | 12.9초 | 10.0초 | 10.2초 | 23.7초(VLM 동시 2 판독 중, ×1.8) |
| OCR 호출 중앙값 | 0.69초 | 1.04초 | 2.58초 | 1.26초 |
| VLM 200영역 판독(cache-bust) | 797초 | 554초(−30%) | 489초(−39%) | 629초(동시 2 + OCR, +13%) |
| VLM 호출 중앙값/최대 | 11/69초 | 21/59초 | 34/117초 | 18/99초 |
| 판독 실패(퇴화 출력) | 2 | 0 | 0 | 2 |
| 페이지 평가: 소속 영역 정확 / 누락 | 858 / 5 | 889 / 8 | 895 / 4 | 854 / 10 |

- **OCR**: 서버 추론이 직렬이라 동시성을 올려도 대기열 지연만 늘었다. 출력은 16/16 페이지가 같다. 기본값은 동시 1을 유지한다.
- **VLM**: 동시 2와 4에서 벽시계 시간이 줄었다. 동시 4는 호출당 지연이 크게 늘었다.
- **혼합**: OCR과 VLM이 서로를 늦춘다(OCR ×1.8, VLM +13%).
- **품질과 동시성은 이번 측정으로 구분할 수 없다**:
  - 같은 temperature 0 설정에서도 실행마다 판독 실패(0~2건, 같은 소형 표들의 출력 퇴화)와 문구가 달라졌다. 동시 1 기준으로 정규화 후 10~13% 영역의 문구가 달랐다.
  - 페이지 평가 지표도 854~895로 흔들렸다.
  - cache-bust 식별자 줄 자체가 출력에 영향을 줬을 가능성도 배제하지 않는다(cached c1 883 vs cache-bust c1 858).
- **기본값**: VLM 동시성은 1로 둔다. 운영 동시성은 처리 시간 목표와 공유 GPU 정책이 정해진 뒤 고른다. 후보는 동시 2(−30%)다.
- 근거: `work/compare/concurrency.md`, `work/runs/ocr-c*`, `work/pipeline/full-c*`, `work/pipeline/nc-c*`.
