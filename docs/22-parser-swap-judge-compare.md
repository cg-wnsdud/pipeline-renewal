# 22. 파서 교체 판정 비교와 판독 수정 2건(2026-10-29)

nh-ad-compliance 의 기존 파서(nh-parser-fin, P1/P3)를 이 파이프라인으로 바꾸기 전에, 같은 광고를 두 파서의 결과로 **실제 판정기**
(작업기 `TemplateReviewJudge` → 판정 엔진 chunking·runner → 모델)에 넣어 판정이 어떻게 달라지는지 비교했다. 비교에서 찾은 새 파서
판독 오류 2건을 고쳤다(5b493a5).

## 1. 비교 방법

| 항목 | 내용 |
|---|---|
| 광고 | 전량 테스트 dm05(입출식 상품 페이지 PDF 2쪽), mx1306(입출식 통장 + 적립식 적금 혼합 PDF 1쪽), td01(거치식 HWP 1쪽). 기존 파서 결과(2026-10-23 P3 v11)가 있는 광고 |
| 기존 파서 | 저장된 P3 를 판정기에 그대로 넣음 |
| 새 파서 1차 | 이 저장소에서 `scripts/run_service.py` 직접 실행(수정 전 0fe9572) → 실행 폴더 ZIP 을 작업기 `read_parser_archive` 로 읽음 |
| 새 파서 2차 | nh-ad-compliance 작업 트리의 `parser-pipeline/`(5b493a5 스냅숏)을 실제 파서 서비스(`apps/parser`, FastAPI)로 띄우고 작업기 파서 클라이언트(`NhParserClient`)로 `POST /v1/parse`(fileId, templateId 반복) → ZIP → 판정용 보기 → 판정. 운영과 같은 경로(Python 3.11, uv.lock). 다른 점은 로컬 Windows 글꼴·HWP 변환기 환경 |
| 등록 템플릿 | 기존 결과와 같은 템플릿을 등록한 것으로 보냄(dm05·td01 하나 = fixed, mx1306 둘 = restricted) |
| 산출물 | `work/judge-compare-2026-10-29/`(1차), `work/service-compare-2026-10-29/`(2차, `report.html` = 비교 리포트) |

## 2. 1차 비교(수정 전)

판정 76개 행 중 71개가 같고 5개가 달랐다. 원본 이미지·판독 기록과 대조한 원인:

| 광고 · 규칙 | 기존 → 새 | 원인 |
|---|---|---|
| dm05 유의사항 줄바꿈 | 적정 → 부적정 | **새 파서 오류.** 표 후보 영역을 셀 재판독(table-cells/1)이 '표 아님'으로 답하면서 행을 한 줄로 이어 쓴 문구를 돌려줬고 그 문구가 최종 문구가 됐다. 원본은 `·` 항목마다 줄이 나뉜다 |
| mx1306 적금 이자지급제한 | 적정 → 확인필요 | **새 파서 오류.** 압류 안내 문구는 기존과 같은데 `digit_mismatch` 가 붙어 판정이 판독 불가로 보류했다. OCR 이 '1661-3000, 1522-3000' 을 '3000,1522' 로 붙여 읽었고 숫자 비교가 이를 천 단위 숫자 하나로 봤다 |
| mx1306 통장 금리 3개 행 | 부적정 → 확인필요 | 배너 가운데 장식 그래픽 '0%' 를 기존 파서는 '0%+' 로 읽어 연 단위·세전 없는 금리로 판정됐고, 새 파서는 이 그래픽 글자를 읽지 않았다. 금리 표시로 볼지는 심의 기준 문제라 **로직을 그대로 둔다**(사용자 결정 2026-10-29) |

세 광고에서 판독 품질 사유가 붙은 영역 9개 중 6개가 `digit_mismatch` 였고 6개 모두 OCR 쪽이 틀렸다(1397 → 139, ☎ → 8, 쉼표로 이어진 두 번호).

## 3. 수정(5b493a5)

1. **숫자 비교**(`text_eval.digit_groups`): 판독 검사의 OCR↔VLM 숫자 비교(`digit_mismatch`, 재판독 조건 `ocr_digits_missing_in_page_read`)는
   천 단위 쉼표(3,000)만 붙이고 그 밖의 쉼표·점은 구분자로 본다. 날짜·소수점의 띄어쓰기 차이도 같은 덩어리가 된다. 정답 대조용
   `digits` 는 그대로다.
2. **HWP 원문 숫자**: HWP 구조 영역(문구 = HWP 원문)의 숫자 불일치는 렌더 OCR 쪽 차이라 품질 사유가 아니라 맥락 사유
   `ocr_hwp_digit_mismatch` 로 둔다(심의 입력의 판독 품질 사유에서 빠짐).
3. **표 아님 셀 재판독**(`table_cells.with_line_breaks`): 셀 재판독이 `is_table=false` 면 문구 글자는 재판독 것(더 큰 crop 이라 dm05 에서
   '1397' 을 맞게 읽음)을 쓰고 줄바꿈 위치는 1차 판독에서 옮긴다. 공백을 뺀 두 문구를 글자 단위로 맞춰, 1차 줄바꿈 앞 글자 바로 뒤의 공백
   (없으면 줄바꿈 뒤 글자 바로 앞의 공백)을 줄바꿈으로 바꾼다. 공백이 없는 자리는 건드리지 않고 글자는 바꾸지 않는다. 옮긴 수는
   trace `line_breaks_from_first_read`. 셀 재판독 지시에 줄바꿈 지시를 더한 /2 는 계약 통과가 나빠 이미 기각했으므로(docs/11) 지시는 그대로 둔다.

확인: dm05 '기타사항' 영역 줄바꿈 13개 중 13개를 옮겼고 글자는 재판독 문구와 같다. mx1306 압류 안내 영역의 `digit_mismatch` 가 없어졌다.
단위 테스트 159개 통과.

## 5. 반복 실행(mx1306)

파싱·판정이 모두 모델 호출이라 같은 입력에서도 실행마다 결과가 달라진다. mx1306 을 수정 후 서비스 경로로 세 번(N1~N3) 파싱·판정하고,
기존 파서 P3 도 매번 다시 판정했다(L1~L4, L1 은 1차 비교 때). N0 은 수정 전 1차 비교다. 판정이 한 번이라도 달랐던 행만 적었다

## 6. 남은 문제

- **장식 그래픽 글자 누락**: 판독 지시에 '그림 속 글자도 전사' 가 있어도 배너의 큰 장식 '0%' 를 읽지 않았다. 금리 표시로 볼지 정하지 않아 그대로 둔다.
- **상품 소속 판단의 실행 간 차이**: 같은 문구의 표가 실행마다 다른 상품으로 배정됐다. 소속이 틀리면 두 상품의 규칙이 함께 흔들린다.
  표 안의 '「NH올원e통장」에서 출금하여' 가 통장 쪽 신호로 읽혔을 가능성이 있다(추정, 확인하지 않음). 배정에 위치(같은 단의 상품명) 정보를 어떻게 쓰는지 살펴볼 후보다.
- **판독 순서가 섞이는 영역**: 왼쪽 라벨 2줄·오른쪽 값 2줄 배치의 짧은 영역(중도해지·만기후 금리)을 세 번 모두 원본과 다른 순서로 읽었고
  매번 다르게 섞였다. `reading_order_conflict`(단순 세로 배치 검사)는 한 번만 잡았다. 판정은 보류(확인필요)로 끝났지만 라벨-값 2열 배치의
  순서 검사·판독 지시를 살펴볼 후보다.
- **판정 모델의 실행 간 차이**: 같은 P3 를 다시 판정해도 행이 바뀐다(위 표). 파서 교체 효과를 볼 때는 여러 번 실행한 분포로 봐야 한다.
- 이번 비교는 광고 3건이다. 대출·투자·퇴직연금·상품명 미노출 광고와 여러 파일 묶음은 비교하지 않았다.
