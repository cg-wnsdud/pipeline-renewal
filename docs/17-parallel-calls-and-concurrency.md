# 17. VLM 호출 병렬화 정리·죽은 코드 정리·동시 상한 확인(2026-10-28)

파이프라인 구조 점검(병렬/직렬 호출 구간)에서 찾은 직렬 구간 두 곳을 고치고, 어디서도 호출하지 않는 코드를 지웠다. 그리고 VLM 동시 상한(`--vlm-concurrency`,
기본 2)을 3·4로 올려도 되는지 같은 작업량으로 다시 측정했다. 최종 JSON(layout-result/2·/3) 구조와 판독·분류 규칙은 바꾸지 않았다.

## 1. 바꾼 것

| 구간 | 이전 | 이후 | 위치 |
|---|---|---|---|
| 긴 이미지 자동 경계 관계 판정(relation/2) | 경계 후보를 하나씩 직렬 호출 | 한 라운드의 판정 대상(서로 독립)을 `--vlm-concurrency` 상한으로 동시 호출. 라운드는 앞 판정에 의존하므로 순서대로 | `auto_boundary.make_plan(concurrency)`, `stage1.run(vlm_concurrency)` |
| 페이지 판독 → 영역 확인(재판독·표 셀) | 모든 페이지·타일·띠의 1차 판독이 끝난 뒤 영역 확인 시작 | 판독 단위 하나의 1차 판독이 끝나면 그 단위의 영역 확인을 같은 풀에 바로 넣음. 풀은 넣은 순서로 처리해 1차 판독이 먼저 나가고 영역 확인이 빈 자리를 채움 | `read_stage.Reader.read_pages_page_first`, `verify_work` |
| 시간 기록 | 경계 판정 VLM 시간이 stage1(OCR) 벽시계에 섞임 | `stage1/run.json` 의 `auto_boundary_timing`(탐색 OCR·판정 시간·호출·라운드 수), `trace/timing.json` 의 `stage1.auto_boundary_judge_seconds` | `stage1.py`, `scripts/run_pipeline.py` |

결과가 같다는 근거:

- 경계: 판정 결과는 위치(y)로 모으므로 호출 순서와 무관하다. 같은 응답이면 같은 계획(cuts·rounds·거부 위치)이 나온다(테스트로 확인).
- 판독: 병합(`merge_entries`)은 호출 번호 순서로 영역마다 결과를 합친다. 한 영역의 영역 확인은 그 영역 1차 판독이 끝난 뒤에만 호출되므로
  영역별 호출 순서는 이전과 같다. 저장 응답 재구성(`--rebuild`)도 같은 순서를 쓴다.

## 2. 지운 것(호출처 없음)

모듈·이름까지 따지는 참조 검사(AST)로 운영 코드(`layout_pipeline/`, `scripts/`)에서 쓰이지 않는 정의를 찾았다. 지운 정의만 검사하던 테스트도 지웠다.

| 위치 | 내용 |
|---|---|
| `file_result.export_run` | layout-result/1 실행을 /2 로 내보내기(호출 없음) |
| `stage1.rebuild`, `_view_from` | 저장 OCR 로 Stage 1 재빌드(호출 없음) |
| `vlm_tasks.page_request`(page/1), `cross_region_duplicates` | page/2(`page_read.page_request`)로 대체 / 측정용(호출 없음) |
| `table_cells.cells_cover`, `cells_text`, `CELLS_COVER_MIN` | 호출 없음 |
| `vlm_contract.merge_results`, `READ_RESULT_SCHEMA`, `TABLE_RESULT_SCHEMA` | Stage 1 시절 결과 병합 계약(테스트만) |
| `text_eval.evaluate_region`, `evaluate_page` 와 그 보조(`precision_side`, `support_mask`, `membership` 등) | 정답 대비 문구 평가(eval/2, 테스트만). 남은 `text_eval` 은 판독 검사용 정규화·비교 도구 |
| `routing.compose_sequence`, `tile_length_bounds` | 실제 구성은 `compose_sections`(테스트만) |
| `boundary.accept_m2`, `relation_request`, `RELATIONS`, `M1_GAP_RATIO` | 이전 M1/M2 경계 실험. 실제 판정은 `auto_boundary`(테스트만) |
| `assignment.INK_RULE`·`ink_check`, `ink.py` | ink-containment/1 비교안. 실행 옵션에 선택지가 없음(테스트만) |
| `semantic_assets.catalog` | `ad_templates.json` 로더(호출 없음). 파일은 출처·해시 기록으로 남기고, 라벨 스키마와의 일치 검사는 테스트가 파일을 직접 읽어 계속한다 |
| `page_read.BAND_VERSION` | 기록하지 않는 버전 상수 |

남긴 것: 기본값이 아닌 실행 옵션으로만 도는 비교·재현 경로(`--read-mode crop`, `--verify-mode patch`, `--table-read legacy`,
`--assignment-rule overlap-best`, `--classification-mode legacy` 등)와 매 실행 돌지만 최종 결과에 쓰이지 않는 Stage 1 진단(정답 대조·`vlm_plan`·
`server_blocks`)은 이번 범위가 아니다.

## 3. 테스트

`pytest` 126개 통과(이전 131개 − 지운 함수 전용 7개 + 새 2개). 새 테스트:

- `test_auto_boundary_judges_one_round_concurrently_with_same_plan`: 동시 3으로 판정해도 최대 동시 호출이 1보다 크고 직렬 판정과 같은 계획.
- `test_reread_starts_without_waiting_for_other_page_reads`: 페이지 a 의 재판독이 페이지 b 의 1차 판독 중에 시작된다. 이전 코드에서는 실패한다(확인함).

## 4. 측정

조건: tp01(긴 이미지 545×8192, 7타일)·tp02(긴 이미지 1080×8192, 4타일)·tp03(2쪽 PDF)을 한 manifest(`work/manifests/conc-2026-10-28.json`,
입력 하나 = 묶음 하나)로 실행. 동시 2는 새 코드 전체 실행, 동시 3·4는 동시 2의 Stage 1 을 재사용(`--from-stage1`)해 판독·보충·의미 단계만 실행.
세 실행 모두 `--cache-bust`(판독 호출의 서버 prefix cache 재사용 방지). 공유 GPU(GB10 1대, vLLM·PaddleX 공용)이고 다른 사용자 부하는 통제하지
않았다. 조건마다 1회. 실행 폴더 `work/pipeline/conc-2026-10-28-c{2,3,4}`, 실행 스크립트 `work/run-conc-2026-10-28.sh`.

### 4.1 경계 판정 병렬화(동시 2)

| 페이지 | 판정 호출·라운드 | 이전(직렬, 오전 e2e) | 이후(라운드 안 동시 2) |
|---|---|---:|---:|
| tp01_p01 | 6호출·1라운드 | 38.0초 | 26.9초(−29%) |
| tp02_p01 | 12호출·6라운드 | 64.0초 | 53.8초(−16%) |

- 경계 결과(cuts·라운드별 판정 대상)는 오전 실행과 같다. tp02 의 거부 위치 사유 일부는 다르게 나왔다(같은 요청 반복 시 응답 변동).
- 호출당 지연 중앙값이 5.3초(직렬)에서 8.5초(2개 동시)로 늘어 기대(약 −50%)보다 덜 줄었다.

### 4.2 재판독 대기 구간 제거(동시 2)

가장 긴 1차 판독(tp03_p02, 26영역, 81.6초)이 도는 동안 다른 자리에서 다른 단위의 재판독 12회(합 69초)가 먼저 처리됐다. 이전 방식이면 이 자리는
69초 동안 비고 그 재판독이 뒤로 밀렸으므로, 이 작업량에서 판독 단계 약 35초(판독 265초의 약 12%) 단축으로 추정한다. 판독·보충 구간의 빈 자리는
동시 2에서 9.7초(295초 중)다.

### 4.3 동시 2·3·4

| 항목 | 동시 2 | 동시 3 | 동시 4 |
|---|---:|---:|---:|
| 판독 단계(페이지·재판독·표 셀) | 264.9초 | 252.1초(−5%) | 258.5초(−2%) |
| 보충 | 30.8초 | 34.0초 | 31.6초 |
| 의미 단계(묶음 3개) | 122.5초 | 98.9초(−19%) | 93.3초(−24%) |
| Stage 1 이후 전체 | 약 420초 | 386.8초(−8%) | 384.7초(−8%) |
| 판독 처리량(전체 토큰/초) | 613 | 630(+3%) | 654(+7%) |
| 의미 단계 처리량(전체 토큰/초) | 759 | 896(+18%) | 1,049(+38%) |
| 페이지 판독 지연 중앙값/최대 | 18.6 / 81.6초 | 25.2 / 97.7초 | 34.3 / 110.0초 |
| 재판독 지연 중앙값 | 5.9초 | 10.6초 | 17.2초 |
| HTTP·계약 오류, finish≠stop | 0, 0 | 0, 0 | 0, 0 |
| read_failed 영역 | 1 | 0 | 1 |
| 동시 2와 정규화 문구 같은 영역 | 176/176(기준) | 158/176 | 162/176 |
| 상품·템플릿 | 기준 | 같음 | 같음 |

- **판독 단계는 동시 2에서 이미 서버 처리량이 포화**다. 동시를 올리면 처리량은 3~7%만 늘고 호출마다 그만큼 느려져 벽시계가 거의 같다.
  동시 4에서는 가장 긴 페이지 호출(81.6→110초)과 그 뒤에만 시작할 수 있는 재판독이 끝 시간을 정한다.
- **의미 단계는 동시 3·4에서 줄었다.** 묶음 3개의 관측(observe) 호출이 동시 2에서는 2개만 함께 돌고, 이미지 없는 라벨 호출이 많아 처리량도 늘었다.
- 판독은 큰 이미지 2장을 보내는 요청이고 의미 단계 라벨은 글자만 보낸다. 판독만 포화되는 원인은 이미지 처리 쪽으로 추정하나 서버 설정(동시 처리
  수·스케줄러)은 프록시 뒤라 확인하지 못했다.
- 문구 차이(8~10%)·read_failed·영역 배정 수 차이는 같은 동시성에서도 실행마다 나는 변동 범위(docs/03 E2: 10~13%)와 구분할 수 없다.
- docs/03 E2(동시 4 −39%)는 영역 crop 묶음 판독(crop 모드) 측정이라 지금의 페이지 우선 판독과 작업 형태가 다르다.

결론: 기본값은 동시 2로 유지한다. 판독 단계는 3·4로 올려도 빨라지지 않고 공유 GPU 의 다른 작업만 느려진다. 묶음 여러 개를 한 번에 처리하는
운영이라면 의미 단계만 3으로 올리는 선택지가 있다(이 작업량 기준 전체 약 −6%, 의미 단계 상한을 따로 두는 옵션이 필요).
